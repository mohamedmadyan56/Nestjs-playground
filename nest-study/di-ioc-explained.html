1. ما هو Dependency Injection (DI)؟

Dependency Injection هو نمط تصميم (Design Pattern) بيديك طريقة لإزالة الاعتماد المباشر بين الكلاسات. الفكرة إنك بدل ما كل class يخلق dependencies بتاعته بنفسه (باستخدام new)، إنت بتسلمه إياها من برّه — الـ framework هو اللي بيهتم بإنشائها وتمريرها.

🎯 الهدف الأساسي: فصل المسؤوليات (Separation of Concerns) وتقليل الاقتران (Coupling) بين المكونات بحيث الكود يكون أسهل في الصيانة والاختبار.

مثال قبل DI (Bad Practice ❌)

export class UsersService {
  private repo: UsersRepository;

  constructor() {
    // ❌ UsersService بيعتمد على class محدد - Tight Coupling
    this.repo = new UsersRepository();
  }
}

مثال بعد DI (Good Practice ✅)

export class UsersService {
  // ✅ NestJS هو اللي هيحل dependency دي ويحقنها
  constructor(private readonly repo: UsersRepository) {}
}

في المثال التاني، UsersService مش عارف إزاي UsersRepository بيتصنع — هو بس بيطلب الـ instance. NestJS (الـ container) هو اللي بيلاقي instance ويحطها في الـ constructor.

2. Inversion of Control (قلب التحكم)

Inversion of Control (IoC) هو مبدأ أوسع من DI. معناه إنك بتسلم التحكم في تدفق البرنامج لـ framework خارجي. بدل ما الكود بتاعك هو اللي يتحكم في كل حاجة، الـ framework هو اللي يستدعي الكود بتاعك.

IoC vs DI — إيه الفرق؟

  • IoC (قلب التحكم): مبدأ عام — انت بتقول للـ framework: "أنا هكتب الـ logic بس، وإنت تدير الباقي". زي ما NestJS يستدعي Controllers بتاعتك لما يجي Request.
  • DI (حقن التبعيات): تطبيق محدد لمبدأ IoC — الـ framework بيدير تبعيات كل Class ويحقنها فيه.
💡 الخلاصة: كل DI هو IoC، مش كل IoC هو DI. DI هو واحد من طرق تطبيق IoC.

3. كيف يعمل DI في NestJS بالتفصيل؟

NestJS بيستخدم IoC Container (حاوية قلب التحكم) عشان يدير كل الـ dependencies. العملية بتتم على 3 خطوات:

الخطوة 1: التسجيل (Registration)

أول حاجة، لازم تخبر NestJS عن الخدمات المتاحة عن طريق إضافتها في providers array في الـ Module. 

@Module({
  controllers: [UsersController],
  providers:    [UsersService, UsersRepository],
  //              ╚═══════════╝
  //              دي الـ Providers اللي container هيديرها
})
export class UsersModule {}

الخطوة 2: الحل (Resolution)

لما NestJS يحتاج class معين، بيفحص constructor بتاعه ويشوف dependencies المطلوبة. بعد كده بيبحث في الـ registry بتاعه عشان يلاقي instances جاهزة أو يخلق واحدة جديدة.

UsersController بحتاج UsersService │ ▼ IoC Container بيتفقد constructor بتاع UsersService │ ▼ لا حاجة UsersService عنده dependency (UsersRepository) │ ▼ Container بيدور على UsersRepository في providers │ ▼ لو لقاه: بيخلق instance من UsersRepository │ ▼ بيحقن UsersRepository جوه UsersService │ ▼ بيحقن UsersService جوه UsersController

الخطوة 3: الحقن (Injection)

بعد ما الـ Container يحل كل التبعيات، بيحقنها جوه الـ constructors تلقائيًا. أنت بس بتكتب التايب في الـ constructor parameter. 

@Injectable()
export class UsersService {
  constructor(
    private readonly repo: UsersRepository,
    @Inject('CACHE_MANAGER') private cache: Cache,
  ) {}
}
⚡ الـ @Injectable() decorator: بيخبر NestJS إن الـ class ده ممكن يكون عنده dependencies ويحتاج يتعامل معاه الـ IoC Container. لو نسيت تحطها، NestJS مش هيعرف يحقن حاجة فيه.

4. Providers — قلب الـ DI في NestJS

Provider هو أي class أو value أو factory NestJS يقدر يستخدمها ويحقنها في أماكن تانية. كل provider بيتسجل في Module وبيبقى جزء من الـ IoC Container.

أنواع الـ Providers:

  • 🔹 Class Providers — أسهل وأشهر نوع. providers: [UsersService]
  • 🔸 Value Providers — لما تحقن قيمة ثابتة أو object.
  • 🔹 Factory Providers — لما تحتاج منطق معين عشان تنشئ الـ instance.
  • 🔸 Alias Providers — تعمل alias لـ provider موجود.
📌 مهم: Provider بيتحول لـ instance واحدة أو أكتر حسب الـ scope. وكل provider ليه Token مميز بيستخدمه Container للبحث.

5. Injection Tokens

كل provider في Container ليه Token بيميزه. لما NestJS يدور على dependency، بيستخدم الـ Token عشان يلاقيها.

أنواع الـ Tokens:

// 1. Class Token (الأشهر):
providers: [UsersService]
// Token = UsersService class نفسه

// 2. String Token:
providers: [{ provide: 'DATABASE_CONNECTION', useValue: db }]
// Token = 'DATABASE_CONNECTION'

// 3. Symbol Token (للتأكد من التفرد):
export const CACHE = Symbol('CACHE');
providers: [{ provide: CACHE, useClass: RedisCache }]

ازاي تحقنها؟

// Class Token — NestJS بيعرف automatically
constructor(private service: UsersService) {}

// String/Symbol Token — محتاج @Inject()
constructor(
  @Inject('DATABASE_CONNECTION') private db: Connection
) {}

6. Scopes — نطاقات حياة الـ Provider

كل provider ليه Scope بيحدد مدة حياة الـ instance:

النطاق الوصف الاستخدام
DEFAULT (Singleton) instance واحدة للتطبيق كله الـ default ومثالي لمعظم الحالات
REQUEST instance جديدة لكل incoming request لما تحتاج data خاصة بكل request
TRANSIENT instance جديدة كل ما يحقن في مكان جديد لما كل consumer محتاج نسخته الخاصة
⚠️ تحذير: استخدام REQUEST و TRANSIENT بيأثر على performance لأن كل instance جديد بيتعمل لكل طلب/حقن. استخدمهم بس لما تحتاجهم فعلاً.

7. Custom Providers

في بعض الحالات، محتاج تتحكم في طريقة إنشاء الـ Provider. هنا يجي دور الـ Custom Providers:

useValue — لحقن قيم ثابتة

providers: [
  {
    provide: 'CONFIG',
    useValue: { apiUrl: 'https://api.example.com', port: 3000 },
  },
]

useFactory — منطق ديناميكي للإنشاء

providers: [
  {
    provide: 'DATABASE_CONNECTION',
    useFactory: async (config: ConfigService) => {
      const conn = await createConnection(config.get('db'));
      return conn;
    },
    inject: [ConfigService],  // Dependencies تانية للـ Factory
  },
]

useExisting — Alias لـ Provider موجود

providers: [
  LoggerService,
  {
    provide: 'LOGGER_ALIAS',
    useExisting: LoggerService,
  },
]

8. Modules & DI

الـ Modules في NestJS بتنظم الـ DI Container. كل Module عنده scope خاص بيه من الـ providers:

┌─────────────────────────────────────┐ │ AppModule │ │ ┌──────────────────────────────┐ │ │ │ UsersModule (imports) │ │ │ │ providers: [UsersService] │ │ │ │ exports: [UsersService] │◀──│── يتشارك مع الموديولات التانية │ └──────────────────────────────┘ │ │ ┌──────────────────────────────┐ │ │ │ AuthModule (imports) │ │ │ │ imports: [UsersModule] │ │ │ │ providers: [AuthService] │ │ │ └──────────────────────────────┘ │ └─────────────────────────────────────┘

قواعد مهمة عن الـ Modules Scope:

  • Private by default: الـ providers متاحة بس جوه الـ module نفسهم.
  • Export: عشان تشارك provider مع module تاني، لازم تصدره في exports.
  • Global Modules: لو حطيت @Global()، providers بتاعته متاحة لكل الموديولات من غير ما تستورد.
@Global()  // ✅ متاح لكل حاجة — استخدم بحذر
@Module({
  providers: [CommonService],
  exports:   [CommonService],
})
export class CommonModule {}

9. Circular Dependencies (التبعيات الدائرية)

لما Service A يعتمد على Service B و Service B يعتمد على Service A — ده اسمه Circular Dependency. NestJS مش بيقدر يحل dependencies زي دي بسهولة.

🚨 المشكلة: Container مش هيعرف يخلق A قبل B ولا B قبل A لأن كل واحد بيحتاج التاني.

الحلول:

// الحل 1: Forward Reference (@Inject(forwardRef(...)))
@Injectable()
export class UsersService {
  constructor(
    @Inject(forwardRef(() => AuthService))
    private authService: AuthService,
  ) {}
}

10. الخلاصة — اللي محتاج تفهمه وتذاكره

┌─────────────────────────────────────────────────────────────┐ │ ملخص Dependency Injection في NestJS │ ├─────────────────────────────────────────────────────────────┤ │ │ │ 📦 IoC Container = خريطة (Map) من Token → Instance │ │ │ │ 📝 التسجيل: Module → providers[] │ │ │ │ 🔍 الحل: Container يشوف constructor ويعرف dependencies │ │ │ │ 💉 الحقن: NestJS بيمرر instances للـ constructor تلقائيًا │ │ │ │ 🎯 @Injectable(): يقول لـ NestJS إن الـ class ده قابل للحقن │ │ │ │ 🏷️ Injection Token: Class / String / Symbol │ │ │ │ 🔄 Scope: Singleton (default) | Request | Transient │ │ │ │ 📂 Module Scope: Private بإفتراضي — Export للمشاركة │ │ │ └─────────────────────────────────────────────────────────────┘

أهم النقايط اللي تثبتها:

  • @Injectable() — كل service لازم يكون عنده decorator ده.
  • providers array — سجل كل service في module تبعها.
  • constructor injection — اختصار private readonly في الـ constructor.
  • Singleton by default — نفس الـ instance في كل مكان (مفيد للـ caching, connections).
  • Custom providers — استخدم useValue, useFactory for flexibility.
  • @Inject() — استخدمه مع string/symbol tokens.
  • Exports — عشان تشارك provider برا module.
🔥 الـ Magic وراء NestJS:
NestJS بيستخدم الـ Reflection API (من خلال reflect-metadata) عشان يقرا type hints من constructor parameters في runtime. لما تكتب private repo: UsersRepository، TypeScript بيحفظ metadata إن parameter ده من نوع UsersRepository. NestJS بقرا الميتاداتا دي ويعرف إنه يحتاج يحقن UsersRepository فيه.
